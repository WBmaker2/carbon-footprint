# Priority Roadmap

작성일: 2026-05-07

## 목적

이 문서는 `carbon-footprint` 프로젝트의 현재 분석 결과를 바탕으로, 다음 개선 작업을 어떤 순서로 진행할지 정리한 우선순위 로드맵이다.

현재 앱은 단순 MVP를 넘어 날짜별 기록, 최근 7일 요약, 저장 실패 안내, 레거시 데이터 마이그레이션까지 갖춘 교실 실사용형 정적 웹앱에 가깝다. 따라서 다음 단계는 새 기능을 많이 붙이기보다, 문서 정합성, 교실 운영 UX, 데이터 보존성, 유지보수 구조를 차례로 단단하게 만드는 방향이 적절하다.

## 우선순위 원칙

1. 수업 중 실수나 데이터 손실을 먼저 줄인다.
2. 실제 구현과 문서가 같은 이야기를 하도록 맞춘다.
3. 교사가 바로 체감할 수 있는 운영 기능을 구조 개편보다 먼저 다룬다.
4. 구조 리팩터링은 기능 동작을 보존하면서 작게 나누어 진행한다.
5. 커밋/푸시 이후 보고에는 배포 URL을 항상 포함한다.

현재 배포 URL:

- https://wbmaker2.github.io/carbon-footprint/

## Phase 1. 교실 운영 UX 안전장치

권장 순서: Phase 0 직후

상태: 완료

목표:

- 수업 중 실수로 기록이 사라지거나 교사가 혼란을 겪는 상황을 줄인다.

작업 항목:

- [x] 전체 데이터 삭제 문구를 더 구체화해 브라우저 전체 기록 삭제임을 명확히 한다.
- [x] 저장 실패 상태가 발생했을 때 "현재 화면에는 남아 있지만 새로고침/페이지 닫기 후 사라질 수 있음"을 더 분명히 안내한다.
- [x] 오늘 기록과 과거 날짜 기록을 수정할 때 UI 문구가 정확히 구분되도록 점검한다.
- [x] 공유 기기 수업 종료 맥락에서 전체 삭제/선택 날짜 초기화 동작을 구분해 문구를 정리한다.
- [x] 선택 날짜 기록 초기화에도 확인 게이트를 추가한다.

완료 기준:

- 전체 삭제와 선택 날짜 초기화 모두 의도 확인 후 실행된다.
- 저장 실패 시 사용자가 저장 성공으로 오해하지 않는다.
- 교사가 공유 기기에서 수업을 마칠 때 어떤 버튼을 눌러야 하는지 명확하다.

## Phase 2. 백업/내보내기와 가져오기

권장 순서: 교사 체감 가치가 가장 큰 기능 단계

목표:

- localStorage 단독 저장의 한계를 줄이고, 교사가 수업 기록을 보관하거나 옮길 수 있게 한다.

작업 항목:

- [x] 전체 기록 JSON 내보내기 기능 추가
- [x] JSON 가져오기 기능 추가 (형식 검증 실패 시 기존 기록 유지)
- [x] 가져오기 방식: 병합(기본), 교체 라디오 선택 지원
- [x] 최근 7일 요약 CSV 다운로드 기능 추가
- [x] 백업/복원/CSV 동작을 README 문서화

완료 기준:

- 교사가 한 브라우저의 기록을 파일로 내려받을 수 있다.
- 올바른 백업 파일을 다시 가져오면 날짜별 기록이 복원된다.
- 잘못된 JSON을 가져와도 기존 기록이 유지된다.

상태: 완료

## Phase 3. 저장 계층 계약 정리

권장 순서: 백업 기능 전후로 작게 진행

상태: 완료

목표:

- 저장 실패, 파싱 실패, 마이그레이션 결과를 앱 계층이 명확히 알 수 있게 한다.

작업 항목:

- [x] 저장 API 반환값을 `{ ok, records, error }` 형태로 통일했다.
- [x] `readRawStorage()` 파싱 실패를 조용히 처리하지 않고 읽기 실패 상태를 노출한다.
- [x] 저장 실패/읽기 실패를 별도 상태 메시지로 분리해 화면에서 안내한다.
- [x] 레거시 샘플 자동 제거는 실제 사용자 기록 삭제 위험을 낮추기 위해 중단하고, 저장 데이터 sanitize와 전기 필드 마이그레이션만 유지한다.
- [x] `app.js`와 `storage.js`의 날짜 키/파싱 유틸을 `date-utils.js`로 공통화한다.

완료 기준:

- 저장 실패와 읽기 실패가 서로 다른 상태로 표현된다.
- 파손된 저장 데이터가 "기록 없음"처럼 조용히 처리되지 않는다.
- 마이그레이션과 레거시 샘플 보존 정책을 테스트나 문서로 설명할 수 있다.

## Phase 4. 앱 구조 리팩터링

권장 순서: 기능 안정화 후

상태: 완료

목표:

- `app.js`에 모인 계산, 렌더링, 이벤트 처리를 분리해 다음 기능 추가 비용을 낮춘다.

작업 항목:

- [x] 날짜 유틸을 `date-utils.js` 기준으로 사용하도록 정리한다.
- [x] 탄소 계산과 요약 view model 생성을 `calculations.js`로 분리한다.
- [x] 히스토리 목록과 요약 카드 렌더링이 계산된 view model을 받아 DOM에 반영하도록 정리한다.
- [x] 전역 스크립트 로드 순서 의존을 줄이기 위해 ES module 전환을 검토한다.
- [x] Chart.js CDN 정책을 결정한다. 이번 Phase에서는 정적 앱 호환성과 fallback 유지를 이유로 CDN을 유지한다.

완료 기준:

- 계산 로직을 DOM 없이 검증할 수 있다.
- 렌더링 함수는 계산보다 화면 반영에 집중한다.
- 기능 추가 시 `app.js` 한 파일을 크게 건드리지 않아도 된다.

완료 메모:

- `calculations.js`가 `getTotalCarbon`, `getControllableCarbon`, `getStudentActionCount`, `getTopItem`, `getEcoLevel`, `buildSummaryViewModel`, `buildWeeklySummaryViewModel` 등을 전역 `window.CarbonTrackerCalculations`로 제공한다.
- ES module 전환은 보류했다. 현재 앱은 빌드 도구 없이 GitHub Pages에서 정적 파일로 동작하며, 전환 시 스크립트 로드/브라우저 파일 실행 호환성 검증 범위가 커진다.
- 레거시 샘플 자동 제거는 Phase 4 이후 구조에서도 다시 추가하지 않는다. 현재 `storage.js`는 날짜 키와 상태 값을 sanitize한 뒤 사용자 기록으로 보존하며, 과거 전기 필드만 현재 데이터 모델로 변환한다.
- Chart.js는 CDN을 유지하되, `window.Chart`가 없을 때 일간/주간 그래프 fallback 문구를 보여주는 정책을 README와 MVP_SPEC에 명시했다.

- 공개 URL 확인은 변경 사항이 `main`에 병합되고 GitHub Pages에 반영된 뒤 최종 릴리스 보고에 기록한다.
